# Spec 04: Database — Broken Fresh-Install Migration, Schema Hazards, Pool Duplication

- **Priority:** high
- **Effort:** M
- **Category:** correctness

## Problem(s)

### 04.1 First migration fails on a fresh database
`migrations/20260116094605_create_cached_files_table.sql:5-14`: the table is created with
```sql
id INTEGER NOT NULL PRIMARY KEY DEFAULT nextval('cached_files_id_seq'::regclass)
```
*before* `CREATE SEQUENCE IF NOT EXISTS cached_files_id_seq` (line 14). On an empty database the `'cached_files_id_seq'::regclass` cast fails ("relation does not exist"), the migration errors, and `main.rs:48-50` aborts startup. The service only works on databases where the sequence already existed (pre-sqlx-migrate legacy). Any fresh deploy or dev environment is broken.

**Fix:** Move `CREATE SEQUENCE IF NOT EXISTS` before `CREATE TABLE`, or use `id INTEGER GENERATED BY DEFAULT AS IDENTITY` / `SERIAL`. Since the migration already ran in prod, either fix it in place (checksum change requires care with `_sqlx_migrations`) or document the reconciliation step.

### 04.2 Global unique index on `message_id` alone can reject valid rows
`migrations/20260116094605_create_cached_files_table.sql:29`:
```sql
CREATE UNIQUE INDEX IF NOT EXISTS ix_cached_files_message_id ON cached_files (message_id);
```
Message IDs are only unique per chat. The config supports multiple bots (`BOT_TOKENS`, `src/config.rs:21`) and the files server chooses `chat_id` (`src/services/telegram_files/mod.rs:17-20`), so two files in different chats can legitimately share a `message_id`. The INSERT in `cache_file` (`src/services/mod.rs:178-191`) then fails — and with the current `unwrap()` aborts the process (Spec 02.2). The composite constraint `uc_cached_files_message_id_chat_id` (line 41) is the correct one; the single-column unique index makes it unreachable and redundant.

**Fix:** New migration: `DROP INDEX IF EXISTS ix_cached_files_message_id;` keep the `(message_id, chat_id)` unique constraint.

### 04.3 Cache insert has no `ON CONFLICT` — concurrent misses race
`src/services/mod.rs:178-191`: two concurrent requests for the same uncached `(object_id, object_type, is_normalized)` both pass the SELECT at lines 61-72, both download+upload, and the second INSERT violates `uc_cached_files_object_id_object_type_is_normalized` → panic. It also uploads the file to Telegram twice (orphan message).

**Fix:** `INSERT ... ON CONFLICT (object_id, object_type, is_normalized) DO UPDATE SET message_id = EXCLUDED.message_id, chat_id = EXCLUDED.chat_id RETURNING *` (or `DO NOTHING` + re-select), plus optionally a per-key in-process single-flight (e.g. `moka` entry API) to avoid double downloads.

### 04.4 Two connection pools are created; the migration pool leaks
- `src/main.rs:44` — `db::get_pg_pool().await` (used only for migrations).
- `src/views.rs:193` — `get_router()` calls `get_pg_pool().await` again.

Result: 2 × `max_connections(10)` pools; the first sits idle holding connections for the process lifetime.

**Fix:** Create one pool in `main`, run migrations on it, and pass it into `get_router(pool)`.

### 04.5 Pool tuning: 300-second acquire timeout
`src/db.rs:15-17`:
```rust
.max_connections(10)
.acquire_timeout(std::time::Duration::from_secs(300))
```
Under pool exhaustion each handler blocks up to 5 minutes before erroring — far beyond any client timeout, amplifying pile-ups.

**Fix:** Reduce `acquire_timeout` to a few seconds; make pool size configurable via env.

### 04.6 Redundant single-column indexes
`migrations/20260116094605_create_cached_files_table.sql:30-31`: `ix_cached_files_object_id` and `ix_cached_files_object_type` are unnecessary — every query filters on `(object_id, object_type, is_normalized)` (`src/services/mod.rs:61-72,333-341`; `src/views.rs:137-148`), which is covered by the unique constraint's index. `object_type` alone is a low-cardinality index that only slows writes.

**Fix:** Drop both single-column indexes in a new migration.

## Acceptance criteria
- `sqlx migrate run` succeeds on a completely empty database, and the app boots.
- No unique index on `message_id` alone; `(message_id, chat_id)` uniqueness remains.
- Concurrent first-time requests for the same object result in exactly one row, no panic, and (ideally) one upload.
- Exactly one `PgPool` exists at runtime; acquire timeout ≤ 10s.
